# 称重软件对接 · 服务端配合事项清单

> 依据：[API对接方案-称重软件.md](./API对接方案-称重软件.md)
> 背景：称重软件端（C# WinForms，精锐计量称重软件）已按方案完成平台对接开发，
> 含 HMAC-SHA256 签名、5 个开放接口调用、本地推送队列（照片先传后绑、指数退避重试、断网续传）。
> 本文列出**服务端（Django 平台）需要开发、调整与确认的事项**，供排期与联调使用。

---

## 一、必须调整/开发的项

### 1. blackbox 接口 photoId 改为可选（已确认）

客户端摄像头离线/取图失败时，无照片的黑匣子记录会**省略 photoId 字段**直接上送。
服务端需将 `photoId` 由必填改为可选（字段可空），照常入库，不再做必填校验。

### 2. 批量 results 必须全量逐条返回 ⚠️ 高优先级

`/records` 与 `/blackbox` 的 `results` 数组必须包含**所有**提交的 clientRef
（`created` / `duplicate` / `failed` 三态），不能只返回失败条目。

客户端按 clientRef 逐条回填状态：
- 命中 `created` / `duplicate` → 标记完成；
- 命中 `failed` → 标记失败并展示 reason；
- **未出现在 results 中的条目 → 按可重试异常处理**（会反复重试，浪费双方资源）。

### 3. clientRef 唯一索引按凭证（AppKey）维度建 ⚠️ 高优先级

不要按站或全局唯一。同一计量站允许多张凭证（多台地磅各一套软件），不同凭证之间存在撞号可能。
幂等唯一约束应为：**`(credential, client_ref)`**。

### 4. clientRef 不要按建议格式强校验

客户端实际格式（≤64 字符、凭证内唯一即可）：

| 数据 | 实际格式示例 | 说明 |
| --- | --- | --- |
| 称重记录 | `20260930-01-0001` | 本地流水号：日期-磅号-序号 |
| 黑匣子记录 | `BX42` | `BX` + 本地自增 Id |
| 照片 | `captures/20260930/20260930-01-0001_cam1`<br>`blackbox/20260930/103412_123_cam1` | 相对路径去扩展名，**含斜杠** |

服务端只校验"非空、≤64 字符"即可，`client_ref` 字段需允许 `/` 字符。

### 5. 凭证管理功能可用

管理端「计量站管理」需提供：生成 / 重置 / 启用 / 停用，密钥仅生成时明文展示一次。
**联调前需下发一对 AppKey/AppSecret 给称重软件现场**（每台地磅一张凭证）。

### 6. 照片 24h 清理任务边界

只清理**未被任何记录/黑匣子引用**的照片；被引用后永久保留。
客户端长断网 >24h 恢复后会重传照片（同 clientRef 幂等返回同 photoId），
清理逻辑不能误删"上传超 24h 但随后被记录引用"的照片（重传后引用即挂载）。

### 7. HTTPS 证书

客户端走操作系统信任链。需**有效 CA 证书**；如平台使用自签/内部 CA 证书，
握手会失败，需提前提供正式证书或根证书部署方案。

## 二、联调协议细节（最易踩坑，请逐条核对实现）

| # | 细节 | 客户端实现口径 |
| --- | --- | --- |
| 1 | GET 也要验签 | ping（GET）bodyHash = `SHA256("")`（空串哈希） |
| 2 | multipart 签名 | bodyHash = `SHA256(appKey + timestamp + fileSize + fileSha256)`，fileSha256 在表单字段；timestamp 为毫秒；signature 为小写十六进制 |
| 3 | 空字段省略 | 客户端 JSON 忽略 null 字段：`driverPhone` / `cargoOwnerName` / `variety` / `weigher` / `plateNo` / `photos` 可能缺失，blackbox 的 `photoId` 可能缺失——反序列化需容忍字段缺失；`landownerPhone` 恒有（可能为空串，按非法返回单条 failed 即可） |
| 4 | 时间格式 | `weighTime` / `weighedAt` / `shotAt` 均为 `yyyy-MM-dd HH:mm:ss` 东八区字符串 |
| 5 | 失败 reason 文案 | 单条 failed 的 reason 面向现场人员，要可读（如"地主电话格式非法""photoId 不存在"），不要只回错误码 |
| 6 | photoId 校验范围 | records.photos[] 校验"**本凭证**已上传且未过期"，跨凭证引用按单条 failed |
| 7 | 限流 | 数据接口 60 次/分、照片上传 120 次/分（按 appKey，Redis 计数）。客户端实测峰值：照片 ≤40/分、记录 ≤2 批/分、黑匣子 ≤1 批/分，余量充足 |
| 8 | 401 不区分原因 | 按方案返回统一 `401 + code=1000` 即可；客户端统一提示"检查 AppKey/AppSecret 与本机系统时间" |
| 9 | 净重为负 | 正常流程不会出现（见三-1），保留单条 failed 兜底即可 |

## 三、服务端可依赖的客户端行为前提

1. **毛 ≥ 皮恒成立**：客户端二次磅结算时已按"大者为毛、小者为皮"落库，
   正常流程不会产生负净重。
2. **推送时机**：仅"已完成"的完整称重业务推送（一次磅/未完成不推）；
   作废请求恒晚于记录推送到达（客户端队列同轮先记录后作废）。
3. **重试节奏**（服务端依赖 clientRef 幂等兜底，重复请求恒返回 duplicate）：
   - 网络/5xx/超时：按 1m / 5m / 15m / 1h / 6h 退避，最多重试 5 次后置失败、停止自动重试；
   - 限流 429：15 秒后重试（不计入退避次数）；
   - 鉴权失败 / 单条业务校验失败：立即停止重试，置失败状态等待人工处理。
4. **多磅部署要求**：同一站多套称重软件必须配置**不同磅号**
   （客户端流水号含磅号，磅号相同会撞 clientRef），部署清单需写明。

## 四、联调验收清单（建议服务端自测通过后再约联调）

1. ping：正确密钥返回 stationCode/stationName；篡改任一签名参数 → 401；
   相同 nonce 重放 → 401；时间戳偏差 >300s → 401。
2. 照片：上传返回 photoId 且可访问；同 clientRef 重传幂等返回同 photoId；
   被记录引用后不被 24h 清理任务删除。
3. 批量：50 条含 3 条非法 → 47 条 created、3 条 failed 且 **results 共 50 条**。
4. 幂等：同 clientRef 重推 → duplicate，库中仅一条。
5. 黑匣子：**无 photoId 的记录正常入库**（本次新增行为，务必覆盖）；
   批量 200 条（含重复）逐条结果正确。
6. 作废：`voided` / `already_voided` / `not_found` 三态正确返回；作废不可逆。
7. 归属匹配：地主电话已注册 → 农户端可见；双电话均未注册 → unmatched 且记录照常入库；
   管理端"重新匹配"可补绑。
